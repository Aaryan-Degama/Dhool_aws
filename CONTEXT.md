## Project: Dhool

- **Name:** Dhool (धूल, "dust"). Full design is in `DHOOL.md`.
- **Track:** Waste and Energy (rooftop solar).
- **Problem statement:** Rooftop-solar households see a daily kWh number and can't tell whether it is good, so losses from dust, faults or haze go unnoticed.
- **Target users:** PM Surya Ghar homeowners with small (1–3 kW) systems.
- **Core feature (the one that must work):** screenshot or inverter data in → expected output from pvlib + Open-Meteo weather → one verdict (CLEAN / INSPECT / WAIT) → verify recovery afterwards.
- **Stack:** pvlib physics baseline plus explainable rules (LightGBM and Laya optional), mock inverter API serving a simulated neighbourhood.
- **Languages:** English and Hindi, fixed text in both (decided Oct 10; see Log).
- **End product:** mobile-first React PWA on Amplify Hosting (the URL judges open), wrapped with Capacitor as an Android APK from the same code. The wrapper is the first thing to cut. The inverter API is called by the backend, so it does not affect the frontend choice.
- **AWS usage:** SAM CLI, Lambda (zip and container images), ECR, API Gateway (HTTP API), Cognito, S3, DynamoDB, EventBridge, Amplify Hosting, CloudWatch.
- **Backend (decided Oct 10):** AWS SAM, Python 3.12 Lambdas behind an HTTP API, one `template.yaml`. Analysis functions (pvlib) ship as a Lambda container image; plain API handlers stay zip. Region ap-south-1 if the Bedrock vision model is available there. Chosen because pvlib is Python and the same stack is what ships after the hackathon.
- **Auth and households (decided Oct 10):** Cognito user pool (email) with an HTTP API JWT authorizer. Data belongs to a **house**, not a person: every family member has their own login and sees the same screenshots, readings, inverter connection and verdicts. The first person creates the house (`owner`) and shares a 6-character invite code (DynamoDB TTL, 7 days); others join with it (`member`). Identity is the token `sub`; every handler calls one `authorize(sub, house_id, action)` and logs the decision as one JSON line. Owner-only: create invite, remove member, disconnect inverter. Judges get two pre-created demo accounts in one demo house.
- **DynamoDB (one table, on-demand, `Query` only):** `HOUSE#<id>` with `META`, `MEMBER#<sub>`, `READING#<date>`, `VERDICT#<date>`; `USER#<sub>` → `HOUSE#<id>` lookup; `INVITE#<code>` with `expiresAt` TTL. Screenshots in S3 under `houses/<id>/`, reached only through presigned URLs issued after `authorize()`.
- **Self-hosted models on CPU (decided Oct 10; replaces the Textract and templates-only plan, since Textract and Bedrock are both blocked on the Free plan):**
  - **Vision:** Qwen3-VL-2B-Instruct (Apache-2.0, confirmed) through llama.cpp in a Lambda container; built and deployed Oct 10 (see Done so far). Text (explanations, vendor messages) stays on fixed templates for now.
  - **Laya (fine-tuned Oct 10, not deployed, not used by the app):** `convaiinnovations/laya` multilingual checkpoint (mmBERT, 322M, 644 MB, Apache 2.0, `laya` 0.3.24, revision `55cf4c4`), tuned to sort a vendor's reply to the "Message your vendor" request into `visit_scheduled`, `asking_details`, `refused`, `unclear`. See Done so far.
  - **Hosting (decided Oct 10):** a Lambda container called in the background (upload → job → result on the screenshot's DynamoDB item → the app asks for it). SageMaker Serverless was ruled out: its 60 s limit is shorter than one read on CPU.
  - **Guardrails that stay:** the verdict and every number come from code, never from a model; the user confirms the kWh read from a screenshot; manual entry and fixed templates remain as fallbacks.
  - The Strands agent stays dropped (it needs a hosted model API). Say openly in the write-up that Bedrock and Textract were unavailable on the Free plan. **Oct 10: AWS Support rejected the Bedrock request, so this is final.**
- **Dropped up front:** LightGBM, Step Functions, vendor view, neighbour map, Capacitor APK. Add back only if Day 3 ends early.
- **Day-by-day plan:** `DHOOL.md` 2.16, with these changes: Day 1 also stands up Cognito, the house and invite flow, CI and the Amplify-connected live URL; household sharing joins the never-cut list.

- **Verdict rules, deployed (Oct 10):** `backend/dhool/verdict.py` returns CLEAN / INSPECT / WAIT / OK with a cause (fault, trips, haze, dust, unclear, no_data), confidence, a plain-language reason, loss in %, kWh/day and ₹/week, and the evidence (fault date, dust rate, days since cleaning, PM2.5). Order of rules: sudden drop that stays and the area did not share → INSPECT; repeated one-day dips → INSPECT; within 5% of the roof's own normal → OK; hazy air and the area fell together → WAIT; steady decline since last rain or wash → CLEAN, or WAIT if 5 mm of rain is forecast within 2 days; otherwise WAIT with low confidence. `evaluate.py` scores the rules against the simulator's known causes: **91% accuracy on seed 0 (the development data), 92% on seed 7 (never used for tuning)**, 1,290 checks each. INSPECT precision 1.00, recall 0.99–1.00. CLEAN precision 0.97–0.99, recall 0.76–0.80. Known weakness: WAIT precision about 0.5, because borderline dust cases fall back to WAIT or OK; the errors are on the cautious side.

- **Screenshot reading with a real vision model (Oct 10, deployed):**
  - **The model:** Qwen3-VL-2B-Instruct (Apache-2.0), the Qwen team's 4-bit GGUF (`Q4_K_M` 1.1 GB + vision projector `Q8_0` 445 MB, revision `52d6c8f`, hash-checked by `scripts/fetch-model.sh`), served by llama.cpp's `llama-server` built from source at release `b11351`, inside a Lambda container (`vision/`, `VisionFunction`, 3008 MB: the most this account's Lambda allows, which gives two cores). Replaces the dummy reader, which only read data hidden in the demo images.
  - **How it asks:** narrow questions, not one broad one. First "is this a list of days, a today summary, or neither", then either "copy the rows" or "today's figure" and "its date". Asked broadly ("list every daily value"), the model invented rows by pinning today's number on every date under a chart; that failure is now a test case, and a list whose rows all share one value is rejected. Charts are never read. The picture is the shared start of every question, so it is taken in once.
  - **Flow:** upload to S3 through a signed slot (PNG or JPEG, 5 MB, deleted after 30 days) → `POST .../screenshots/read` starts the reader in the background and returns 202 → the app asks `GET .../screenshots/{shotId}` every 4 s → the API keeps only values that can be true for the roof (a date with no date printed becomes the upload day) → the homeowner checks and corrects every number in editable boxes → only then `POST .../readings` saves them. Failures and a reader that never answers (15 min) show as "could not read".
  - **Measured on the demo screens** (each saved image carries the printed numbers as hidden text, its answer key; the reader never sees it): all 93 printed values on 9 screens read exactly and none invented, at picture ceilings of 1024, 640, 400 and 256 tokens on a laptop; settled on 640 for margin. In the Lambda image with two cores and a 3008 MB cap: a 15-day list takes about 63 s and a today screen about 48 s, peaking at about 2.7 GB. Live on AWS (Oct 10): the first read in a fresh container took 5.5 minutes, about four of them fetching the 1.6 GB of weights from the container image; with the reader warm, a 15-day list came back in about 2 minutes and a today screen in about 80 seconds, from choosing the file to seeing the numbers. A ping every five minutes (EventBridge) keeps one container loaded and primes it with a one-word prompt, which pulls the weights in (priming a fresh container took 3 min 24 s). A screenshot of Dhool's own roof screen was refused, as it should be: the model's figure "Units possible" fails a last yes/no check that the label says generated today. Scored again after that check on 17 images (the 9 demo inverter screens and 8 screenshots of Dhool and other screens): 93/93 values exact, nothing invented. Lambda reports its memory at the 3008 MB ceiling while reading; an 8-bit attention cache would save 170 MB but made the model misread, so it is not used.

- **Laya wired in: the vendor's reply, read (Oct 10, deployed):**
  - **What it does:** on a "Call your vendor" verdict the homeowner pastes the vendor's WhatsApp reply; `POST /houses/{id}/vendor-reply {text}` returns one of `visit_scheduled`, `asking_details`, `refused`, `unclear`; the app shows the four kinds as buttons with that one selected and the next step for it. The homeowner can change it. Nothing is stored and the text is never logged. "They are coming" points to the existing "The vendor has visited" check.
  - **How it runs:** `MessageFunction`, a Lambda container (`messages/`: `laya` 0.3.24 with ONNX Runtime 1.30, the **v3.2 int8 weights** (335 MB), 3 GB image, 3008 MB), called by the API and kept loaded by a five-minute ping. Warm: about 250 ms in the Lambda, 0.6 s through the API, 1.8 GB max memory. Cold: about a minute (the limit is 5 minutes). First deployed with v3 in PyTorch (0.4 s, 2.6 GB) and switched to v3.2 the same day, as the owner asked: 144 of 156 on the test sets against v3's 147. PyTorch is still in the image only because the `laya` package imports it. If the reader is down, slow or returns anything but the four labels, the API answers 503 and the four buttons work by hand.

- **Accuracy rework, hidden test set, real-rooftop check, and the wash / visit check (Oct 10; on branch `accuracy-verification`, not deployed until merged):**
  - **What was wrong:** the rules measured "now" with a week's median, which describes the roof about three days ago. While dust built it under-read the loss (dusty roofs called OK); right after rain it still showed the old dirt (clean roofs called "unclear").
  - **Rule changes (`verdict.py`):** the roof's level is measured since its last cleaning (rain of 5 mm, a wash or visit the homeowner reported, or a jump in the data) and moved forward along the recent trend; rain or a reported wash in the last day or two gives OK until clear days confirm it; the dust rate is read from both the last 30 days and the whole dry spell; a roof's sudden drop is judged against its neighbours' change, so a fault is found even when rain lifts everyone else that week; the roof's normal is its best weeks, not its best single days; the size of drop that counts as a fault scales with how much that roof's own data wanders; one-day dips ("trips") are only called when neighbours exist, since alone they are usually clouds the weather data missed.
  - **Development neighbourhoods (Delhi, seeds 0, 1, 2):** 96% (was 92–94%). INSPECT precision 1.00, recall 0.99–1.00; CLEAN precision 0.96–0.98, recall 0.89–0.90; WAIT precision 0.64–0.97 (was 0.26–0.55; the low seed has dusty roofs in a hazy spell that get the haze WAIT).

CLEAN precision 0.95, recall 0.73; INSPECT precision 0.97, recall 0.86; OK precision 0.89, recall 0.96; WAIT precision 0.02 (only 25 true WAIT cases; 286 dusty roofs got the cautious "unclear" WAIT). The misses are cautious: 17 faults were called CLEAN and 11 dusty roofs INSPECT. **Do not tune against this set.** If the rules change, rerun and report the new number as it comes.
  - **Real rooftops (`python -m dhool.realcheck`):** nine homes in California and Arizona from NREL PVDAQ (PVOutput.org systems, daily kWh, about ten years each, CC BY 4.0). No labels, so no accuracy number. Findings: real output scatters 3–8% a day around the physics (the simulator assumes 2%); after 115 first rains following 60+ dry days output rose 72% of the time, median +4%; where the roof was 5%+ below its normal before the rain, the loss predicted +12.8% and +5.5% came back, so on real roofs rain explains under half of the measured gap (the rest is seasonal model error: unknown tilt, clipping, shading). Before the noise-aware thresholds the rules said INSPECT in 57% of system-months on these mostly healthy roofs; after, 9% (OK 43%, CLEAN 25%, unclear WAIT 23%). **Honest limit:** on a single real roof with no neighbours, CLEAN and "unclear" are still raised too often; neighbours or a correct tilt and direction are what fix it.

- **Wash plan: clean only when it pays (Oct 10; branch `wash-economics` until merged):** the fixed rule (5% loss, and wait only for rain within 2 days) is replaced by `wash_plan()` in `verdict.py`. A wash wins back today's dust loss every day until something undoes it: the first rain of 5 mm in the 7-day forecast (free cleaning) or the first forecast dust storm (dirties the panels again; `expected.fetch_dust_storms`, the same dust + gusts + visibility rule as the app's sandstorm sky).
