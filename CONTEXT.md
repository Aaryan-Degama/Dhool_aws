## Project: Dhool

- **Name:** Dhool (धूल, "dust"). Full design is in `DHOOL.md`.
- **Track:** Waste and Energy (rooftop solar).
- **Problem statement:** Rooftop-solar households see a daily kWh number and can't tell whether it is good, so losses from dust, faults or haze go unnoticed.
- **Target users:** PM Surya Ghar homeowners with small (1–3 kW) systems.
- **Core feature (the one that must work):** screenshot or inverter data in → expected output from pvlib + Open-Meteo weather → one verdict (CLEAN / INSPECT / WAIT) → verify recovery afterwards.
- **Stack:** pvlib physics baseline plus explainable rules (LightGBM and Laya optional), mock inverter API serving a simulated neighbourhood.
- **End product:** mobile-first React PWA on Amplify Hosting (the URL judges open), wrapped with Capacitor as an Android APK from the same code. The wrapper is the first thing to cut. The inverter API is called by the backend, so it does not affect the frontend choice.
- **AWS usage:** SAM CLI, Strands Agents SDK, Bedrock, Lambda, API Gateway (HTTP API), Cognito, S3, DynamoDB, EventBridge, Amplify Hosting, CloudWatch.
- **Backend (decided Oct 9):** AWS SAM, Python 3.12 Lambdas behind an HTTP API, one `template.yaml`. Analysis functions (pvlib) ship as a Lambda container image; plain API handlers stay zip. Region ap-south-1 if the Bedrock vision model is available there. Chosen because pvlib is Python and the same stack is what ships after the hackathon.
- **Auth and households (decided Oct 9):** Cognito user pool (email) with an HTTP API JWT authorizer. Data belongs to a **house**, not a person: every family member has their own login and sees the same screenshots, readings, inverter connection and verdicts. The first person creates the house (`owner`) and shares a 6-character invite code (DynamoDB TTL, 7 days); others join with it (`member`). Identity is the token `sub`; every handler calls one `authorize(sub, house_id, action)` and logs the decision as one JSON line. Owner-only: create invite, remove member, disconnect inverter. Judges get two pre-created demo accounts in one demo house.
- **DynamoDB (one table, on-demand, `Query` only):** `HOUSE#<id>` with `META`, `MEMBER#<sub>`, `READING#<date>`, `VERDICT#<date>`; `USER#<sub>` → `HOUSE#<id>` lookup; `INVITE#<code>` with `expiresAt` TTL. Screenshots in S3 under `houses/<id>/`, reached only through presigned URLs issued after `authorize()`.
- **Self-hosted models on CPU (decided Oct 9; replaces the Textract and templates-only plan, since Textract and Bedrock are both blocked on the Free plan):**
  - **Vision:** Qwen3-VL-2B-Instruct (Apache-2.0, confirmed) through llama.cpp in a Lambda container; built and deployed Oct 9 (see Done so far). Text (explanations, vendor messages) stays on fixed templates for now.
  - **Laya:** `convaiinnovations/laya` multilingual checkpoint (mmBERT, 322M, about 647 MB, Apache 2.0, `laya` Python SDK), on CPU, for sorting homeowner messages and reading vendor replies. Its own page reports 0.362 accuracy without fine-tuning on its benchmark, so measure it on our cases first and fine-tune only if needed.
  - **Hosting (decided Oct 9):** a Lambda container called in the background (upload → job → result on the screenshot's DynamoDB item → the app asks for it). SageMaker Serverless was ruled out: its 60 s limit is shorter than one read on CPU.
  - **Guardrails that stay:** the verdict and every number come from code, never from a model; the user confirms the kWh read from a screenshot; manual entry and fixed templates remain as fallbacks.
  - The Strands agent stays dropped (it needs a hosted model API). Say openly in the write-up that Bedrock and Textract were unavailable on the Free plan.
- **Dropped up front:** LightGBM, Step Functions, vendor view, neighbour map, Capacitor APK. Add back only if Day 3 ends early.
- **Day-by-day plan:** `DHOOL.md` 2.16, with these changes: Day 1 also stands up Cognito, the house and invite flow, CI and the Amplify-connected live URL; household sharing joins the never-cut list.

- **Accuracy rework, hidden test set, real-rooftop check, and the wash / visit check (Oct 9; on branch `accuracy-verification`, not deployed until merged):**
  - **What was wrong:** the rules measured "now" with a week's median, which describes the roof about three days ago. While dust built it under-read the loss (dusty roofs called OK); right after rain it still showed the old dirt (clean roofs called "unclear").
  - **Rule changes (`verdict.py`):** the roof's level is measured since its last cleaning (rain of 5 mm, a wash or visit the homeowner reported, or a jump in the data) and moved forward along the recent trend; rain or a reported wash in the last day or two gives OK until clear days confirm it; the dust rate is read from both the last 30 days and the whole dry spell; a roof's sudden drop is judged against its neighbours' change, so a fault is found even when rain lifts everyone else that week; the roof's normal is its best weeks, not its best single days; the size of drop that counts as a fault scales with how much that roof's own data wanders; one-day dips ("trips") are only called when neighbours exist, since alone they are usually clouds the weather data missed.
  - **Development neighbourhoods (Delhi, seeds 0, 1, 2):** 96% (was 92–94%). INSPECT precision 1.00, recall 0.99–1.00; CLEAN precision 0.96–0.98, recall 0.89–0.90; WAIT precision 0.64–0.97 (was 0.26–0.55; the low seed has dusty roofs in a hazy spell that get the haze WAIT).
  - **Hidden test set (`python -m dhool.evaluate hidden`):** Jaipur, Lucknow and Ahmedabad weather for Oct 2024 to Sep 2025, every simulator setting redrawn and wider (dust 0.1–0.8% a day, noise 1–5%, rain needed to clean 3–10 mm, fault sizes, which homes are faulty, haze strength), up to 15% of readings missing. Rules were frozen at the commit "Hidden test set and wash-check scoring" before its first run and it was run once: **84% over 3,870 checks**. CLEAN precision 0.95, recall 0.73; INSPECT precision 0.97, recall 0.86; OK precision 0.89, recall 0.96; WAIT precision 0.02 (only 25 true WAIT cases; 286 dusty roofs got the cautious "unclear" WAIT). The misses are cautious: 17 faults were called CLEAN and 11 dusty roofs INSPECT. **Do not tune against this set.** If the rules change, rerun and report the new number as it comes.
  - **Real rooftops (`python -m dhool.realcheck`):** nine homes in California and Arizona from NREL PVDAQ (PVOutput.org systems, daily kWh, about ten years each, CC BY 4.0). No labels, so no accuracy number. Findings: real output scatters 3–8% a day around the physics (the simulator assumes 2%); after 115 first rains following 60+ dry days output rose 72% of the time, median +4%; where the roof was 5%+ below its normal before the rain, the loss predicted +12.8% and +5.5% came back, so on real roofs rain explains under half of the measured gap (the rest is seasonal model error: unknown tilt, clipping, shading). Before the noise-aware thresholds the rules said INSPECT in 57% of system-months on these mostly healthy roofs; after, 9% (OK 43%, CLEAN 25%, unclear WAIT 23%). **Honest limit:** on a single real roof with no neighbours, CLEAN and "unclear" are still raised too often; neighbours or a correct tilt and direction are what fix it.
  - **Wash and vendor-visit check:** `POST /houses/{id}/actions {type: wash | visit, date}` (and `{date, remove: true}` to undo) stores `ACTION#<date>`; the analysis compares the week before with the clear days after and puts `check` on the verdict: `waiting`, `verified`, `not_recovered` or `was_fine`, with predicted and observed gain. A wash that changed nothing turns the verdict into INSPECT, cause `not_dust`. - **Wash plan: clean only when it pays (Oct 9; branch `wash-economics` until merged):** the fixed rule (5% loss, and wait only for rain within 2 days) is replaced by `wash_plan()` in `verdict.py`. A wash wins back today's dust loss every day until something undoes it: the first rain of 5 mm in the 7-day forecast (free cleaning) or the first forecast dust storm (dirties the panels again; `expected.fetch_dust_storms`, the same dust + gusts + visibility rule as the app's sandstorm sky). CLEAN only if that saving in ₹ beats `WASH_COST_RS` (₹50, a self-wash in water and effort; `config.py`). Otherwise WAIT, cause `dust`, with `evidence.wait_for`: `rain` ("Wait for the rain"), `dust_storm` ("Wash after the dust storm") or `not_worth_it` ("Not worth washing yet", with the days until it will be). With nothing in the forecast a wash is taken to keep paying for `DRY_SPELL_DAYS` (30): **an assumption, not a measurement**. The verdict's reason states the rupees saved and the cost. The simulator's answer key uses the same plan on the true dust, so what is scored is the measuring.
